# 🎉 lo-cal Claude Code スキル・マーケットプレイス

**「仕様書を作って、仕様書どおりに作る」** を Claude Code で実現する、lo-cal 社内向けのプラグイン配布リポジトリです。

このリポジトリ自体がマーケットプレイス（`lo-cal-skills`）になっていて、プラグインをインストールするだけで全スキルが使えるようになります✨

---

## 🤔 このプラグインでできること

`spec-tools` プラグインひとつで、**設計 → 実装 → レビュー → テスト → セキュリティ／パフォーマンスチェック → 納品資料の書き出し**まで、開発の一連の流れを Claude におまかせできます。

### ✨ 特徴

- 📚 **仕様書ファースト** — コードより先に仕様書！`docs/` の仕様書を「正」として開発を進めるので、仕様と実装がズレません
- 🗣 **話しかけるだけ** — 「仕様書を作って」「実装して」と頼むだけで、適切なスキルが自動で動きます
- 🔍 **実装したら必ずレビュー** — 実装後は仕様書との整合性レビューが自動で走ります。レビュー忘れゼロ！
- 🔁 **テストが通るまで自動修正** — NGでも3回までは自動でリトライ。ただし無限には繰り返しません（ちゃんと上限があります）
- 🛡 **危険なコマンドは強制ブロック** — プロジェクト外への `rm` や `sudo` などは、実行される**前に**フックが自動で止めます
- 📦 **納品までカバー** — 社内用の仕様書から、お客様に渡せる版を書き出せます。`[要確認]` や内部ホスト名などの社外に出せない記述は自動で除去📤
- 📋 **進捗が見える** — どの機能がどこまで進んだか、`docs/実装状況.md` に自動で記録されます

## 🚀 推奨の使い方（開発の流れ）

### STEP 1️⃣ まずは設計から 📝

対象プロジェクトで Claude Code を起動して、こう話しかけます：

> 「**仕様書を作って**」

既存コードがあれば分析して、まだ何も無ければ**対話形式のヒアリング**で、要件定義書・画面設計書・DB設計・詳細設計などを `docs/` に生成します。

### STEP 2️⃣ 仕様書どおりに開発 🔨

> 「**ログイン画面を実装からテストまでやって**」

すると自動でこの流れが回ります：

```
実装 → lint・型チェック・ビルド確認 → 仕様適合レビュー → テスト作成・実行 → 回帰確認
         └─ NGなら自動で修正してリトライ（上限あり）─┘
```

### STEP 3️⃣ リリース前の品質チェック 🔒⚡

> 「**脆弱性がないかチェックして**」「**パフォーマンスを確認して**」

仕様書の認証・認可要件との突き合わせや、N+1・SQL効率・キャッシュ戦略の確認を行い、指摘一覧を提示。**承認した指摘だけ**を修正してテストまで回します。

### STEP 4️⃣ 変更したら仕様書も更新 🔄

> 「**仕様書を更新して**」

コードの変更点を検出して、関係する仕様書だけをきれいに更新します。

### STEP 5️⃣ 納品前にクライアント向けのテスト項目書も 📋

> 「**受け入れテスト項目書を作って**」

画面設計書・要件定義書をもとに、クライアントが実際に操作して確認できる平易な言葉のチェックリストを作成。文末には検収の署名欄も付きます。開発前（設計書だけの段階）でも作成でき、機能が増えたら「更新して」で差分だけ追記（記入済みの結果は上書きしません）。「**Excelでもほしい**」と言えば、会員関連・注文関連…のように業務ドメインごとにシートを分けたExcelファイルも追加で作れます。

### STEP 6️⃣ お客様に渡す仕様書を書き出す 📦

> 「**納品用の仕様書を書き出して**」

`docs/` にある社内用の仕様書から、**そのままお客様に渡せる版**を `docs/納品用/` に書き出します。

**① どれを出すか選ぶ** — チェックボックスが出るので、渡す資料にチェックを入れるだけ。「納品向き（推奨）」「契約・納品範囲による（要判断）」「通常は社内用（非推奨）」に分かれていて、それぞれ何が書かれた資料かの説明つきです：

```
納品用に書き出す資料を選んでください（複数選択できます）

［納品向き］
 ☑ 要件定義書          システムの目的・できること・満たすべき条件
 ☑ 画面設計書（12画面） 画面の一覧・つながり・入力項目と操作
 ☑ DB設計              管理する情報。テーブル名・カラム名は業務用語に書き直します
 ☑ 詳細設計（8件）      API・バッチ等。「機能ごとに何ができるか」として要約します

［要判断］
 ☐ インフラ構成書       運用・保守も納品範囲に含む場合に。取り扱い注意
 ☑ 受け入れテスト項目書 検収資料として一緒に渡す場合に

［社内用］
 ☐ 開発環境セットアップ ソースコードごと納品する場合のみ
 ☐ 変更履歴            社内の作業履歴。通常はお客様に渡しません
```

**お客様に渡すものを勝手に決めることはありません。**「おまかせ」で自動選択もしませんし、1件もチェックが無ければ書き出しに進みません。社内用のものにチェックが入っていたときは、理由を添えて一度確認します。

2回目以降は、前回納品した資料に `[前回納品済み]` が付きます（`☐ インフラ構成書　[前回納品済み] 運用・保守も納品範囲に含む場合に`）。前回お渡ししたものをチェックし忘れないための目印です。

**② 技術者向けの記述を、お客様が読める内容に整える** ✂️

元の仕様書は開発者向けに書かれています。納品用では**技術的な記述をそのまま出さず、業務の言葉に言い換えて要約**します。

| 消すもの | 業務の言葉に言い換えるもの | そのまま残すもの |
|---------|--------------------------|----------------|
| `[要確認]` の未確定事項、TODO・FIXME、社内担当者名・チケット番号、リポジトリURL・ブランチ名、内部ホスト名・内部IP、クラス名・関数名・ファイルパス、サンプルコード・SQL・cron式 | API仕様 →「何ができる機能か」／テーブル名・カラム名・型 →「管理する情報の項目（必須・最大◯文字）」／ER図 → 業務用語のラベルに／内部処理の流れ → 利用者から見た手順に／例外名 →「どんなエラーがいつ出るか」 | 機能仕様・画面仕様・入力チェックの内容・業務フロー・権限の違い・件数や期間の上限（**お客様が判断に使う情報**なので削りません） |

仕様そのもの（機能・条件・数値）は足しませんし、変えません。「未実装」を「対応済み」に書き換えるようなこともしません。

**仕様が決まるまでの経緯も載せません** 📅 — 「いつ・誰と・どう決めたか」「当初はB案だったが変更」といった経過や、「運用負荷を考慮して◯◯方式を採用」のような採用理由・却下案は削除し、**決まった結果だけ**を載せます。各ファイル冒頭の「最終更新 YYYY-MM-DD」「バージョン vX.X」のスタンプと変更履歴も出しません。

> 消すのは「いつ決めたか」「いつ更新したか」の日付だけです。**稼働開始日・データの保持期間・締め日・集計対象期間**のように、お客様が運用で必要とする日付は仕様そのものなので残ります（`index.md` の提出日も残ります）。

**③ 元と同じ構成で `docs/納品用/` に書き出し** 🗂

```
docs/
├── 要件定義書.md            ← 元の仕様書（社内用。こちらが常に「正」）
├── 画面設計書/
├── 詳細設計/
└── 納品用/                  ← お客様提出用（🔒凍結）
    ├── index.md            ← 提出日・収録資料の一覧
    ├── 要件定義書.md
    ├── 画面設計書/
    └── 詳細設計/
```

元の `docs/` は**読み取り専用**として扱うので、書き出しても1文字も変わりません。納品用に入らない資料へのリンクは自動で外れるので、リンク切れも起きません🔗

**④ 何を削り・何を言い換えたかを報告** 📄 — そのまま提出してよいか、目視で最終確認できます。

```
■ 除去した内容
| 資料 | 種別 | 除去した内容 |
|------|------|------------|
| 要件定義書 | [要確認] | 「帳票の出力形式」が未確定のまま記載されていたため除去 |
| システム構成書 | 内部ホスト名 | バッチサーバーのホスト名を [ホスト名 - 記載不可] にマスク |

■ 業務の言葉に言い換え・要約した内容
| 資料 | 元の記述 | 納品用での表記 |
|------|---------|--------------|
| 詳細設計/API_ユーザー管理 | POST /api/v1/users ほかCRUD 5本 | 「利用者を登録・変更・削除する機能」として業務説明に要約 |
| DB設計 | テーブル名・カラム名・型・制約（12テーブル） | 「システムが管理する情報」として日本語の項目一覧に変換 |

⚠️ [要確認] を1件除去しています。未確定のまま納品すると認識の相違が起きるため、
内容を確定させてから提出することをおすすめします。
```

> 🔒 **書き出した `docs/納品用/` は「凍結」されます。**
> お客様に提出済みの成果物なので、**そのあとコードや仕様書を変更しても、勝手に修正されることはありません**（「納品用も更新しますか？」と聞くこともしません）。開発・テスト・レビュー・監査でも**読み込みません**（仕様の正は常に `docs/` 直下の元の仕様書です）。
> もう一度書き出したいときは「納品用の仕様書を書き出して」ともう一度伝えてください。**前回の書き出し結果に対する差分更新**になります。「追加 / 更新 / 据え置き / 選択外」の一覧と、更新内容の要約を先に提示するので、中身を確認してから適用できます。内容が同じファイルには触れません。
> **前回納品したのに今回チェックが入っていない資料**があれば、「収録を維持 / 削除 / 今回の選択に加える」を1件ずつ聞きます（勝手に消すことも、黙って残すこともしません）。チェックボックスにも `[前回納品済み]` と表示されるので、選び忘れに気づけます。
> ゼロから作り直したいときは「**納品用を一度削除して作り直して**」と伝えてください。`docs/納品用/` をすべて消してから新規に書き出します（前回の内容は残らず、どこが変わったかも追えなくなるので、削除前に確認が入ります）。

### 🏃 仕様書なしでサクッと開発したいときは？

使い捨てスクリプトなど、仕様書が大げさな場面もありますよね。そんなときは：

> 「**仕様書なしで**実装して」

と**明示**すればOK！仕様適合レビュー等の品質保証が付かない旨を確認したうえで、通常の Claude Code として開発します（危険コマンドのブロックだけは常時有効です🛡）。

## 🧰 スキル一覧

| スキル | なにをする？ |
|--------|-------------|
| 🏗 **architecture-design** | リポジトリを分析して（開発前なら対話で）、要件定義書・システム構成書・画面設計書・DB設計・詳細設計などのMarkdown仕様書を `docs/` に作成・更新・再作成 |
| 🎯 **spec-dev-cycle** | 開発作業の**唯一の窓口**！依頼を聞いて、下の5つの内部スキルをどの順序で使うか判断・実行するオーケストレーター |
| 🔨 spec-implementation | （内部）仕様書＋モック（任意）をもとにコードを実装。実装後のレビューまでセットで実行 |
| 🔍 spec-review | （内部）実装が仕様書・コーディング規約とズレていないかレビュー |
| 🧪 spec-test | （内部）仕様書から正常系・異常系・境界値のテストケースを洗い出してテストコードを作成 |
| 🛡 spec-security | （内部）仕様書の認証・認可要件と実装を突き合わせ、IDOR・インジェクション等の脆弱性をチェック |
| ⚡ spec-performance | （内部）N+1クエリ・SQL効率・キャッシュ戦略をDB設計・非機能要件と照らして確認 |
| 📋 **acceptance-test-writer** | 画面設計書・要件定義書をもとに、クライアント向けの受け入れテスト項目書（UAT資料）を作成。検収署名欄つき。開発前でも作成でき、希望すればドメイン別シート分けのExcelも出力 |
| 🔎 **spec-alignment-audit** | プロジェクト全体で仕様書と実装コードを突き合わせ、「仕様書にあるが未実装」「実装にあるが仕様書に未記載」を1件ずつ確認しながら解決。仕様書・実装コードの両方が揃っているプロジェクト向け |
| 🧩 **spec-consistency-check** | 開発着手**前**に、仕様書どうし（要件定義書↔画面設計書↔詳細設計↔DB設計）の相互参照の矛盾・抜けを1件ずつ確認しながら解決。コードが無くても実行可 |
| 📖 **user-manual-writer** | 画面設計書をもとに、実際にシステムを使う人向けの操作マニュアルを作成。手順書き・スクリーンショットつき。希望すればWord/PDFも出力 |
| 🧑‍🦳 **persona-review** | 技術に詳しくない「利用者ペルソナ」の視点で仕様書または実際のシステムを検証し、分かりにくさ・運用と合わない部分を重要度つきレポートとして出力。開発前でも、実装後は実機操作でも実行できる |
| 📦 **delivery-spec-export** | 開発者向けに書かれた仕様書から、お客様に渡す納品版を `docs/納品用/` に書き出す。対象資料は区分（推奨 / 要判断 / 非推奨）つきのチェックボックスで必ず選択させる（自動選択はしない）。仕様決定の経緯・採用理由・最終更新日/バージョンのスタンプ・変更履歴は載せず、決まった結果だけを出力（稼働開始日・保持期間など仕様そのものの日付は残す）。`[要確認]`・TODO・内部ホスト名などの社内向け記述を除去したうえで、**クラス名・関数名・内部処理の流れ・API仕様・テーブル名/カラム名/型といった技術的な記述を業務の言葉に言い換えて要約し、技術に詳しくない方でも読めるシンプルな内容に整える**（仕様そのものは足さない・変えない）。何を削り・何を言い換えたかを報告。書き出した納品用は**凍結**（コード・仕様書が変わっても追従せず、開発・テストでも読み込まない）。2回目以降は差分を提示してからの**差分更新**が既定で、全削除しての作り直しは明示的に指示したときだけ |

> 💡 「（内部）」のスキルは直接呼び出す必要はありません。**普通に話しかければ spec-dev-cycle がぜんぶ交通整理してくれます**。開発系スキルはいずれも `docs/` の仕様書が前提なので、無い場合は先に仕様書作成を案内します。`acceptance-test-writer`・`spec-alignment-audit`・`spec-consistency-check`・`user-manual-writer`・`persona-review`・`delivery-spec-export` は独立スキルなので直接呼び出せます（`acceptance-test-writer` と `persona-review` は `spec-dev-cycle` の開発サイクル完了時に、`spec-consistency-check` と `persona-review` は `architecture-design` の仕様書作成・更新後にも提案されます）。

## ⚠️ 制約事項（安全のためのルール）

安心して任せられるように、プラグイン全体に共通ルールを設けています。

### 🚫 禁止していること

- 🔐 **機密情報の書き込み禁止** — パスワード・APIキー・個人情報は、仕様書にもコードにも絶対に書き込みません
- 🐘 **システム全体の一括実装禁止** — 必ず「どの画面・機能から？」と確認し、機能単位で進めます
- ♾ **無限ループ禁止** — 修正の繰り返しは各ループ最大5回（自動は3回まで、4回目は確認、サイクル全体で合計10回）。上限に達したら潔く中止して報告します
- 👻 **常駐プロセス禁止** — watchモードのテストや開発サーバーは起動しません（テストはワンショット実行）
- 📦 **納品用フォルダの凍結** — `docs/納品用/` は提出済みの成果物。コードや仕様書が変わっても自動で追従修正しませんし、実装・テスト・レビュー・監査でも読み込みません（書き出し直すときは差分を提示して承認を得てから更新）
- 💣 **破壊的コマンド禁止** — プロジェクト外への `rm`・`mv`、`sudo`・`dd`・`mkfs` などは、**同梱フックが実行前に強制ブロック**します。指示ではなく仕組みで守ります💪

### 🤖 自動でやってくれること

- ✅ 実装後の**仕様適合レビュー**（レビューNGなら3回まで自動修正）
- ✅ **lint・型チェック・ビルド**の確認（プロジェクトに設定がある場合）
- ✅ 新規テストに加えて**既存テストも実行して回帰確認**
- ✅ 進捗を `docs/実装状況.md` に記録
- ✅ 仕様が不明な箇所は**着手前にまとめて質問** → 回答を仕様書に反映してから続行
- ✅ テスト失敗の原因が**環境問題**（DB未起動など）なら、無駄に修正せず即報告
- ✅ git 未導入のプロジェクトでは **`git init` を提案**（git なしを選んだ場合は変更前にバックアップを取って、中止時はそこから復元）
- ✅ 機能の区切りで**コミットを提案**（必ず承認制。push はあなたの手で🙌）

## 📦 導入手順

### 🖥 CLI（ターミナル）の場合

1. ターミナルで対象プロジェクトのフォルダに移動して、Claude Code を起動します

   ```bash
   cd あなたのプロジェクト
   claude
   ```

2. チャットに以下を入力して、マーケットプレイスを登録します

   ```

## 🔧 開発・メンテナンス（このリポジトリを触る人向け）

```
claude-skills/                          # = マーケットプレイス lo-cal-skills
├── .claude-plugin/
│   └── marketplace.json                # 配布カタログ

    └── spec-tools/                     # プラグイン
        ├── .claude-plugin/plugin.json  # プラグイン定義（配布時に version を更新）
        ├── hooks/
        │   ├── hooks.json              # PreToolUseフック定義
        │   └── check_destructive.py    # 破壊的コマンドの検査スクリプト
        └── skills/
            ├── 共通ルール.md            # 全スキル共通の絶対禁止事項・トークン節約方針
            ├── architecture-design/    # SKILL.md + references/
            ├── spec-dev-cycle/         # SKILL.md（唯一の窓口）
            ├── spec-implementation/    # SKILL.md（内部スキル）
            ├── spec-review/            # SKILL.md（内部スキル）
            ├── spec-test/              # SKILL.md（内部スキル）
            ├── spec-security/          # SKILL.md（内部スキル）
            ├── spec-performance/       # SKILL.md（内部スキル）
            ├── acceptance-test-writer/ # SKILL.md（独立スキル）
            ├── spec-alignment-audit/   # SKILL.md（独立スキル）
            ├── spec-consistency-check/ # SKILL.md（独立スキル）

- 変更を配布する際は `plugin.json` の `version` を更新する。利用者は `/plugin` から更新できる
