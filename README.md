# 📐 仕様書・AI駆動開発キット for Claude Code

**「仕様書を作って、仕様書どおりに作る」** を Claude Code で実現する、lo-cal 社内向けのプラグイン配布リポジトリです。

このリポジトリ自体がマーケットプレイス（`lo-cal-skills`）になっていて、プラグインをインストールするだけで全スキルが使えるようになります✨

---

## 🤔 このプラグインでできること

`spec-tools` プラグインひとつで、**設計 → 実装 → レビュー → テスト → セキュリティ／パフォーマンスチェック → 納品資料の書き出し**まで、開発の一連の流れを Claude におまかせできます。

### ✨ 特徴

- 📚 **仕様書ファースト** — コードより先に仕様書！`docs/` の仕様書を「正」として開発を進めるので、仕様と実装がズレません
- 🗣 **話しかけるだけ** — 「仕様書を作って」「実装して」と頼むだけで、適切なスキルが自動で動きます
- 🔍 **実装したら必ずレビュー** — 実装後は仕様書との整合性レビューが自動で走ります。レビュー忘れゼロ！
- 🧪 **テストは頼んだときだけ** — 実装のたびに勝手にテストが走って待たされることがありません。頼めば「テストが通るまで」3回まで自動リトライします（無限には繰り返しません）
- 🛡 **危険なコマンドは強制ブロック** — プロジェクト外への `rm` や `sudo` などは、実行される**前に**フックが自動で止めます
- 📦 **納品までカバー** — 社内用の仕様書から、お客様に渡せる版を書き出せます。`[要確認]` や内部ホスト名などの社外に出せない記述は自動で除去📤
- 📋 **進捗が見える** — どの機能がどこまで進んだか、`docs/実装状況.md` に自動で記録されます

### 📤 出力できるもの

| 種類 | 成果物 |
|---|---|
| 📚 **仕様書**（`docs/`） | 要件定義書 / システム構成書 / 画面設計書（画面ごと）/ DB設計 / 詳細設計（API・バッチ・RPA・CSV・外部連携・共通処理）/ システム設定仕様書 / インフラ構成書 / 開発環境セットアップ / コーディング規約 |
| 💻 **コード** | 仕様書どおりの実装コード、テストコード（頼んだときだけ） |
| 📋 **クライアント向け** | 受け入れテスト項目書（`.md` / `.xlsx`）、操作マニュアル（`.md` / Word / PDF） |
| 📦 **納品用**（`docs/納品用/`） | 仕様書の納品版（`Markdown/`）、サイドバー付きHTML版（`HTML/`）、表紙・目次つき1冊のPDF版（`PDF/`） |
| 🔎 **レポート** | 実装状況（`docs/実装状況.md`）、利用者目線チェック結果、仕様書とコードの乖離・仕様書間の不整合の一覧 |

## 🚀 推奨の使い方（開発の流れ）

### STEP 1️⃣ まずは設計から 📝

対象プロジェクトで Claude Code を起動して、こう話しかけます：

> 「**仕様書を作って**」

既存コードがあれば分析して、まだ何も無ければ**対話形式のヒアリング**で、要件定義書・画面設計書・DB設計・詳細設計などを `docs/` に生成します。

### STEP 2️⃣ 仕様書どおりに開発 🔨

> 「**ログイン画面を実装からテストまでやって**」

すると自動でこの流れが回ります：

```
実装 → lint・型チェック・ビルド確認 → 仕様適合レビュー → テスト作成・実行 → 回帰確認
         └─ NGなら自動で修正してリトライ（上限あり）─┘
```

### STEP 3️⃣ リリース前の品質チェック 🔒⚡

> 「**脆弱性がないかチェックして**」「**パフォーマンスを確認して**」

仕様書の認証・認可要件との突き合わせや、N+1・SQL効率・キャッシュ戦略の確認を行い、指摘一覧を提示。**承認した指摘だけ**を修正してテストまで回します。

### STEP 4️⃣ 変更したら仕様書も更新 🔄

> 「**仕様書を更新して**」

コードの変更点を検出して、関係する仕様書だけをきれいに更新します。

### STEP 5️⃣ 納品前にクライアント向けのテスト項目書も 📋

> 「**受け入れテスト項目書を作って**」

画面設計書・要件定義書をもとに、クライアントが実際に操作して確認できる平易な言葉のチェックリストを作成。文末には検収の署名欄も付きます。開発前（設計書だけの段階）でも作成でき、機能が増えたら「更新して」で差分だけ追記（記入済みの結果は上書きしません）。「**Excelでもほしい**」と言えば、会員関連・注文関連…のように業務ドメインごとにシートを分けたExcelファイルも追加で作れます。

### STEP 6️⃣ お客様に渡す仕様書を書き出す 📦

> 「**納品用の仕様書を書き出して**」

`docs/` の社内用の仕様書から、そのままお客様に渡せる版を `docs/納品用/Markdown/` に書き出します。

**どれを出すかはチェックボックスで必ず選ばせます**（「納品向き」「要判断」「社内用」の区分と説明つき）。おまかせの自動選択はしません。2回目以降は前回渡した資料に `[前回納品済み]` が付くので、選び忘れに気づけます。

書き出すときに整える内容：

- ✂️ `[要確認]`・TODO・内部ホスト名・社内担当者名・クラス名・SQL・cron式などを**除去**
- 🗣 API仕様・テーブル定義・内部処理の流れを**業務の言葉に言い換えて要約**（仕様そのものは足さない・変えない）
- 📅 「いつ・誰と決めたか」「◯◯を採用した理由」といった**経緯は載せず、決まった結果だけ**（稼働開始日・保持期間など仕様そのものの日付は残します）
- 📝 同じ種類の注記の連続をまとめ、常体・敬体の混在や表記ゆれも整える

完了時に、**何を削り・何を言い換えたかを一覧で報告**するので、提出前に目視で確認できます。元の `docs/` は読み取り専用なので1文字も変わりません。

> 🔒 **書き出した `docs/納品用/` は「凍結」されます。** お客様に提出済みの成果物なので、そのあとコードや仕様書が変わっても勝手に修正されません。開発・テスト・監査でも読み込みません。
> もう一度書き出すと**前回との差分更新**になり、「追加 / 更新 / 据え置き / 選択外」を提示してから適用します。ゼロから作り直すときは「**納品用を一度削除して作り直して**」と伝えてください。

### STEP 7️⃣ 納品資料をHTML・PDFにする 🖨

> 「**納品用の仕様書をHTMLとPDFにして**」

STEP 6 で書き出したMarkdownを、そのまま配布・印刷できる形に変換します。

| 形 | 出力先 | 中身 |
|---|---|---|
| 🌐 HTML | `docs/納品用/HTML/` | サイドバーに資料一覧・パンくず・前後リンク。共有フォルダに置けばブラウザで読めます |
| 📕 PDF | `docs/納品用/PDF/` | 表紙 → 目次（ページ番号つき）→ 全資料を1冊に統合 |

画面遷移図・ER図は絵として描画され、資料間のリンクもそのまま辿れます。変換後はリンク切れ・変換漏れを機械的に点検し、**0件でないまま「できました」と報告しません**。

> 🔒 **変換元は `docs/納品用/Markdown/` に固定です。** `docs/` 直下の社内用は変換しません（`[要確認]` や内部ホスト名が入ったまま、表紙と目次の付いた立派なPDFになると、そのまま提出される事故が起きるため）。
> 必要なもの: Python 3・`markdown`・`pypdf`・Google Chrome。図はCDNから描画するので、完全オフラインでは図がテキスト表示になります。

### 🏃 仕様書なしでサクッと開発したいときは？

使い捨てスクリプトなど、仕様書が大げさな場面もありますよね。そんなときは：

> 「**仕様書なしで**実装して」

と**明示**すればOK！仕様適合レビュー等の品質保証が付かない旨を確認したうえで、通常の Claude Code として開発します（危険コマンドのブロックだけは常時有効です🛡）。

## 🧰 スキル一覧

| スキル | なにをする？ |
|--------|-------------|
| 🏗 **architecture-design** | リポジトリを分析して（開発前なら対話で）、要件定義書・システム構成書・画面設計書・DB設計・詳細設計などのMarkdown仕様書を `docs/` に作成・更新・再作成 |
| 🎯 **spec-dev-cycle** | 開発作業の**唯一の窓口**！依頼を聞いて、下の5つの内部スキルをどの順序で使うか判断・実行するオーケストレーター |
| 🔨 spec-implementation | （内部）仕様書＋モック（任意）をもとにコードを実装。実装後のレビューまでセットで実行 |
| 🔍 spec-review | （内部）実装が仕様書・コーディング規約とズレていないかレビュー |
| 🧪 spec-test | （内部）仕様書から正常系・異常系・境界値のテストケースを洗い出してテストコードを作成。**テストを明示的に頼まれたときだけ**動く |
| 🛡 spec-security | （内部）仕様書の認証・認可要件と実装を突き合わせ、IDOR・インジェクション等の脆弱性をチェック |
| ⚡ spec-performance | （内部）N+1クエリ・SQL効率・キャッシュ戦略をDB設計・非機能要件と照らして確認 |
| 📋 **acceptance-test-writer** | 画面設計書・要件定義書をもとに、クライアント向けの受け入れテスト項目書（UAT資料）を作成。検収署名欄つき。開発前でも作成でき、希望すればドメイン別シート分けのExcelも出力 |
| 🔎 **spec-alignment-audit** | プロジェクト全体で仕様書と実装コードを突き合わせ、「仕様書にあるが未実装」「実装にあるが仕様書に未記載」を1件ずつ確認しながら解決。仕様書・実装コードの両方が揃っているプロジェクト向け |
| 🧩 **spec-consistency-check** | 開発着手**前**に、仕様書どうし（要件定義書↔画面設計書↔詳細設計↔DB設計）の相互参照の矛盾・抜けを1件ずつ確認しながら解決。コードが無くても実行可 |
| 📖 **user-manual-writer** | 画面設計書をもとに、実際にシステムを使う人向けの操作マニュアルを作成。手順書き・スクリーンショットつき。希望すればWord/PDFも出力 |
| 🧑‍🦳 **persona-review** | 技術に詳しくない「利用者ペルソナ」の視点で仕様書または実際のシステムを検証し、分かりにくさ・運用と合わない部分を重要度つきレポートとして出力。開発前でも、実装後は実機操作でも実行できる |
| 📦 **delivery-spec-export** | 開発者向けの仕様書から、お客様に渡す納品版を `docs/納品用/Markdown/` に書き出す。対象資料は区分つきチェックボックスで必ず選択させ、社内向けの記述と決定の経緯を除去したうえで、技術的な記述を業務の言葉に言い換えて要約。何を削り・何を言い換えたかを報告する。書き出した納品用は**凍結**（2回目以降は差分更新） |
| 🖨 **delivery-doc-convert** | `docs/納品用/Markdown/` を、サイドバー付きHTML版（`docs/納品用/HTML/`）と表紙・目次つき1冊のPDF版（`docs/納品用/PDF/`）に変換。案件が変わっても同じ体裁で揃う。**変換元は納品用に固定**で、社内向けの記述が残る `docs/` 直下は変換しない |

> 💡 「（内部）」のスキルは直接呼び出す必要はありません。**普通に話しかければ spec-dev-cycle がぜんぶ交通整理してくれます**。開発系スキルはいずれも `docs/` の仕様書が前提なので、無い場合は先に仕様書作成を案内します。`acceptance-test-writer`・`spec-alignment-audit`・`spec-consistency-check`・`user-manual-writer`・`persona-review`・`delivery-spec-export`・`delivery-doc-convert` は独立スキルなので直接呼び出せます（`acceptance-test-writer` と `persona-review` は `spec-dev-cycle` の開発サイクル完了時に、`spec-consistency-check` と `persona-review` は `architecture-design` の仕様書作成・更新後にも提案されます）。

## ⚠️ 制約事項（安全のためのルール）

安心して任せられるように、プラグイン全体に共通ルールを設けています。

### 🚫 禁止していること

- 🔐 **機密情報の書き込み禁止** — パスワード・APIキー・個人情報は、仕様書にもコードにも絶対に書き込みません
- 🐘 **システム全体の一括実装禁止** — 必ず「どの画面・機能から？」と確認し、機能単位で進めます
- ♾ **無限ループ禁止** — 修正の繰り返しは各ループ最大5回（自動は3回まで、4回目は確認、サイクル全体で合計10回）。上限に達したら潔く中止して報告します
- 👻 **常駐プロセス禁止** — watchモードのテストや開発サーバーは起動しません（テストはワンショット実行）
- 🧪 **頼んでいないテストは書きませんし、動かしません** — 作成・修正も**実行**も、「テストを作って」「実装からテストまで」のように明示的に頼んだときだけ（lint・型チェック・ビルドの確認は従来どおり自動）
  - ただし**黙って飛ばしません**。関連する既存テストがあれば「12件あります。実行しますか？」と1回だけ聞き、実行しない場合もテストを**読んで**今回の変更との食い違いを報告します。見つかっても勝手には直さず、実装を直す／テストを直す／今は直さない、を聞きます
- 📝 **同じ種類の注記を連続させない** — `> [!NOTE]` などのAlertは、更新を重ねると同種のブロックが並びがちです。読む側には「別々の注意書き」に見えてしまうため、**仕様書を作る・更新するすべてのスキル**で1つのブロックにまとめます（種類が違うものは重要度が変わるので分けたまま）
- 📦 **納品用フォルダの凍結** — `docs/納品用/` は提出済みの成果物。コードや仕様書が変わっても自動で追従修正しませんし、実装・テスト・レビュー・監査でも読み込みません（書き出し直すときは差分を提示して承認を得てから更新）
- 💣 **破壊的コマンド禁止** — プロジェクト外への `rm`・`mv`、`sudo`・`dd`・`mkfs` などは、**同梱フックが実行前に強制ブロック**します。指示ではなく仕組みで守ります💪

### 🤖 自動でやってくれること

- ✅ 実装後の**仕様適合レビュー**（レビューNGなら3回まで自動修正）
- ✅ **lint・型チェック・ビルド**の確認（プロジェクトに設定がある場合）
- ✅ テストを頼まれたときは**既存テストも実行して回帰確認**（範囲は変更箇所とその依存元に限定）
- ✅ 進捗を `docs/実装状況.md` に記録
- ✅ 仕様が不明な箇所は**着手前にまとめて質問** → 回答を仕様書に反映してから続行
- ✅ テスト失敗の原因が**環境問題**（DB未起動など）なら、無駄に修正せず即報告
- ✅ git 未導入のプロジェクトでは **`git init` を提案**（git なしを選んだ場合は変更前にバックアップを取って、中止時はそこから復元）
- ✅ 機能の区切りで**コミットを提案**（必ず承認制。push はあなたの手で🙌）

## 📦 導入手順

### 🖥 CLI（ターミナル）の場合

1. ターミナルで対象プロジェクトのフォルダに移動して、Claude Code を起動します

   ```bash
   cd あなたのプロジェクト
   claude
   ```

2. チャットに以下を入力して、マーケットプレイスを登録します

   ```
   /plugin marketplace add <このリポジトリのGit URL>
   ```

3. 続けてプラグインをインストールします

   ```
   /plugin install spec-tools@lo-cal-skills
   ```

4. **Claude Code を再起動**します（破壊的コマンドをブロックするフックは再起動後に有効になります🛡）

これで完了！あとは「仕様書を作って」と話しかけるだけです🎉

### 🖱 デスクトップ版（Mac / Windows）の場合

1. Claude Code デスクトップアプリで対象プロジェクトのフォルダを開きます
2. チャット欄に CLI と同じコマンド（`/plugin marketplace add ...` → `/plugin install spec-tools@lo-cal-skills`）を入力します
3. アプリを再起動すれば準備OK！

> 🧪 ローカルで試したい場合は、Git URL の代わりにこのリポジトリのパスも指定できます：
> `/plugin marketplace add /path/to/claude-skills`

### 🔄 更新について（定期的にチェックしてね！）

このプラグインは**どんどん改善・機能追加**しています🚀
`/plugin` を開いて `spec-tools` に更新が来ていないか、**定期的にチェック**してください。更新したら Claude Code の再起動もお忘れなく！
