# 利用者目線ペルソナレビュー・スキル

`docs/画面設計書/` と `docs/要件定義書.md` を情報源に、技術に詳しくない「利用者ペルソナ」に
なりきって仕様（または実際のシステム）を検証し、**実際に使うときにつまずきそうな箇所・
運用と噛み合わない箇所**を洗い出す。

> [!NOTE]
> **開発前（仕様書だけの段階）でも、実装後でも実行できる。** 実装が存在する場合は、実際に
> ブラウザ操作ツールでシステムを操作しながら検証する「実機モード」も選べる（STEP 2 参照）。
> 仕様書だけでは気づけない、実際に触ったときの分かりにくさまで発見できる。

> [!IMPORTANT]
> このスキルは**独立して直接呼び出す**。`spec-dev-cycle`（実装・レビュー・テスト・セキュリティ・
> パフォーマンスの窓口）の内部スキルではない。ただし `architecture-design`（仕様書作成・更新後）
> と `spec-dev-cycle`（開発サイクル完了後）は、それぞれのタイミングでこのスキルの利用を
> 提案してよい（`../architecture-design/SKILL.md` STEP 5、`../spec-dev-cycle/SKILL.md` STEP 6 参照）。

> [!CAUTION]
> `../共通ルール.md` に spec-tools プラグイン全体の絶対禁止事項がある。実機モードで
> ブラウザ操作ツールを使う際も、実在の個人情報・機密情報を入力・記載しない。開発サーバーは
> 検証が終わったら停止し、常駐させない。

---

## STEP 1: 前提確認（必須）

```bash
find docs/ -name "*.md" 2>/dev/null | sort
find docs/画面設計書 -name "*.md" 2>/dev/null | sort
```

- `docs/画面設計書/` と `docs/要件定義書.md` のいずれも見つからない場合 → 実施せず、
  次のように案内して停止する：

  > 「`docs/` に画面設計書・要件定義書が見つかりません。利用者目線レビューにはこれらの
  > 仕様書が必要です。先に architecture-design スキルで仕様書を作成しますか？」

- `docs/要件定義書.md` のみ無い場合は、画面設計書だけで進めてよいかユーザーに確認する
  （対象ユーザー像の手がかりが減る旨を伝える）。
- `docs/画面設計書/` が無い（画面の無いシステム）場合は、このスキルの対象外である旨を伝えて
  停止する（本スキルは「画面を操作する利用者」の視点が前提のため）。

---

## STEP 2: モードの選択（仕様書のみ／実機操作）

```bash
# 実装コードの有無をざっと確認する（依存パッケージ・ビルド成果物は除外。`../共通ルール.md`）
find . \( -name .git -o -name node_modules -o -name vendor -o -name .venv -o -name venv \
  -o -name __pycache__ -o -name dist -o -name build -o -name .next -o -name target \
  -o -path ./docs \) -prune -o -type f -print | head -50
```

| 状況 | モード |
|------|--------|
| 実装コードが見当たらない（開発前モードの設計書のみ） | **仕様書モード**（自動的にこちらになる） |
| 実装コードがあり、dev server 等ですぐ動かせそうな場合 | ユーザーに確認する（下記） |

実装コードが存在する場合は、次のように確認する：

> 「実際にシステムを操作しながら検証しますか？ 仕様書だけの確認より、実際の画面表示・
> 文言・操作感まで踏み込んで問題点を発見できます。
> （a）実際に操作して検証する（開発サーバーの起動が必要です）（推奨）
> （b）仕様書の記載内容だけで検証する」

- **(a) を選んだ場合** → **実機モード**。STEP 5-B に従う。開発サーバーの起動が必要な場合は
  `architecture-design` のスクリーンショット取得時と同様に、起動してよいかをここで確認する
  （確認は最初の1回でよい）。ログイン等の複雑な前提操作が無いと辿り着けない画面は、
  無理に再現せず「未検証」として報告に含めてよい。
- **(b) を選んだ場合** → **仕様書モード**。STEP 5-A に従う。

---

## STEP 3: 利用者ペルソナの決定

以下の**定型ペルソナ**から選んでもらうか、独自のペルソナを自由に記述してもらう。

```
どの利用者ペルソナで検証しますか？（複数選択可、自由記述も可）

(1) ITリテラシーに自信がない高齢者 — 専門用語が分からない、操作に時間がかかる、文字が小さいと読みにくい
(2) 忙しい現場スタッフ — 片手間・急いで操作する、マニュアルを読まず直感で進めようとする
(3) たまにしか使わない一般ユーザー — 前回の操作方法や画面の場所を覚えていない、毎回迷う
(4) スマホ中心でPC操作に不慣れな人 — 右クリック・複数ウィンドウなどPC特有の操作に戸惑う
(5) その他（自由記述で教えてください）
```

- ユーザーが定型ペルソナの番号・自由記述のいずれかで応答したら、それを採用する。
- **ユーザーがこの質問に応答せず読み飛ばした、または「おまかせ」等で判断を委ねてきた場合に限り**、
  `docs/要件定義書.md` の「対象ユーザー」記載をもとにペルソナを自動生成する。この場合は
  生成したペルソナの内容（属性・特徴）を簡潔に提示し、「このペルソナで進めてよいですか？」と
  確認してから STEP 4 に進む。
- 複数ペルソナが選ばれた場合、STEP 5 の分析は**ペルソナごとに**行い、レポートでも
  ペルソナ別に区別する。

---

## STEP 4: チェック観点

各ペルソナで画面・機能を追体験しながら、以下の観点で問題が無いか確認する。

| カテゴリ | 確認する内容 |
|---------|------------|
| 操作の分かりやすさ | ボタン・ラベルの文言が専門用語で分かりにくくないか。次に何をすればよいか画面から読み取れるか |
| エラー・案内メッセージ | エラーメッセージが技術的すぎて、対処法が分からないものになっていないか |
| 前提知識・準備物の要求 | ユーザーが持っていないかもしれない知識・環境・アカウント等を暗黙に要求していないか |
| 例外的な状況への対応 | 入力ミス・通信切断・作業の中断など、想定外の状況からやり直す手段が用意されているか |
| 運用実態との整合性 | 実際の業務フロー・組織の承認体制・繁忙期の使われ方などと仕様が噛み合っているか |
| 取り消し・修正のしやすさ | 誤操作・誤入力に気づいたとき、後から取り消し・修正できるか |
| 完了・処理結果の分かりやすさ | 操作が成功したか失敗したか、処理中かどうかがユーザーに伝わるか |
| アクセシビリティ | 文字サイズ・コントラスト・タップ領域の大きさ、色だけに頼った表現になっていないか（実機モードで特に確認しやすい） |

> [!NOTE]
> 一般的なバグ・実装ミスの指摘は対象外（`spec-review` の役割）。本スキルは**仕様どおりに
> 動いていたとしても、利用者にとって分かりにくい・使いにくい・運用と合わない**という
> 観点に絞る。

---

## STEP 5-A: 分析の実施（仕様書モード）

1. `docs/画面設計書/index.md` と各 `P0X_画面名.md`、`docs/要件定義書.md` の機能一覧・
   対象ユーザー・制約事項を読み込む。
2. 画面ごと・主要な業務フローごとに、選ばれたペルソナがその記載内容だけを頼りに操作したら
   どうなるかを追体験する（**仕様書に書かれていないことを実装済みだと仮定しない**。
   記載が無い箇所は「記載が無いため不明」として扱う）。
3. STEP 4 の観点に照らして問題点があれば記録する。

## STEP 5-B: 分析の実施（実機モード）

1. STEP 2 で確認済みの手順で開発サーバーを起動する（`preview_start` 等）。
2. 選ばれたペルソナになりきり、`docs/画面設計書/index.md` の画面フローに沿って主要な業務フロー
   を実際に操作する（ブラウザ操作ツールで `navigate` → 画面を読む・操作する → 結果を確認する）。
3. STEP 4 の観点に照らして、実際の表示・文言・挙動から問題点を記録する。分かりやすい問題点は
   スクリーンショットを撮って `docs/images/persona-review/` に保存し、レポートから参照する
   （任意。無理に全件撮る必要はない）。
4. ログイン等の前提操作が複雑で辿り着けない画面は無理に再現せず、「未検証」としてレポートの
   末尾にまとめる。
5. 検証が終わったら、起動した開発サーバーを停止する（`../共通ルール.md` の常駐プロセス禁止）。

---

## STEP 6: レポートの作成

見つかった問題点を重要度別に整理し、`docs/利用者目線チェック結果.md` として保存する
（**1件ずつユーザーに確認して解決するフローには入らない**。対応するかどうかの判断は
ユーザーに委ねる）。

### 重要度の目安

| 重要度 | 内容 |
|--------|------|
| 🔴 高 | そのペルソナではタスクを完了できない、または重大な誤操作につながりうる |
| 🟡 中 | 迷う・問い合わせが増える・想定より時間がかかるなど、効率や満足度を下げる |
| 🔵 低 | 改善余地はあるが、致命的ではない |

### ファイル構成

```markdown
# 利用者目線チェック結果

[← ドキュメント一覧に戻る](./index.md)

**実施日**: YYYY-MM-DD
**モード**: 仕様書モード / 実機モード
**対象ペルソナ**: ITリテラシーに自信がない高齢者、忙しい現場スタッフ

---

## ITリテラシーに自信がない高齢者

### 🔴 高 (1件)

- **該当画面・機能**: P03_注文確認画面
- **問題点**: 「確定」ボタンの下に小さい文字で「一度確定すると取り消せません」と
  書かれているが、文字が薄く見落としやすい。注文を誤って確定してしまう可能性がある
- **想定されるシーン**: 急いで最後まで進めた結果、注意書きに気づかないまま確定してしまい、
  後から「間違えた、取り消したい」と問い合わせが来る
- **改善案（提案）**: 確定前に確認ダイアログを挟む、または注意書きを目立つ色・大きさにする

### 🟡 中 (件数)
...

### 🔵 低 (件数)
...

## 忙しい現場スタッフ
...（ペルソナごとに同様の構成）

---

## 未検証の画面・機能（実機モードのみ・該当時）

| 画面・機能 | 理由 |
|-----------|------|
| P08_管理者設定画面 | ログイン後の複雑な前提操作が必要で今回は未検証 |
```

- 既存の `docs/利用者目線チェック結果.md` がある場合は、追記ではなく**その時点の実施内容で
  上書きする**（定点観測のスナップショットとして扱う。過去の実施日・内容は
  `docs/変更履歴.md` に「利用者目線チェックを実施」等、短く記録すれば経緯は追える）。
- `docs/index.md` が存在すれば、ドキュメント一覧に1行追加する（無ければ追加しなくてよい）。

## 品質チェックリスト

- [ ] `docs/画面設計書/` と `docs/要件定義書.md` のいずれも無い場合、実施せず architecture-design を案内している
- [ ] 画面の無いシステムでは対象外である旨を伝えている
- [ ] 実装コードの有無を確認し、実装がある場合は仕様書モード／実機モードをユーザーに確認している
- [ ] 実機モードで開発サーバーを起動する前にユーザーの確認を取っている
- [ ] ペルソナは定型ペルソナ・自由記述のいずれかをまず提示し、ユーザーが応答しなかった場合のみ要件定義書から自動生成し、その内容を確認してから進めている
- [ ] 複数ペルソナが選ばれた場合、分析・レポートをペルソナごとに分けている

- [ ] 仕様書モードで、仕様書に記載の無い挙動を実装済みと仮定していない
- [ ] 実機モードで、ログイン等の前提操作が複雑で辿り着けない画面は無理に再現せず「未検証」として報告している
- [ ] 実機モードの検証後、開発サーバーを停止している(常駐させていない)
- [ ] 見つかった問題点を一覧で提示するだけで終わらせず、重要度（高/中/低）を付けて整理している
- [ ] 1件ずつ確認して解決するフローに入らず、レポートの提示までに留めている（対応判断はユーザーに委ねている）

- [ ] レポートに実施日・モード・対象ペルソナが明記されている
- [ ] 出力先が `docs/利用者目線チェック結果.md` になっている
- [ ] 再実行時は追記ではなく最新の実施内容で上書きしている
- [ ] ブラウザ操作・レポートに実在の個人情報・機密情報を入力・記載していない
