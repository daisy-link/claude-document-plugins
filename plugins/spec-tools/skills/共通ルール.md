# spec-tools 共通ルール

spec-tools プラグインの全スキル（architecture-design・spec-dev-cycle・spec-implementation・
spec-review・spec-test・spec-security・spec-performance・acceptance-test-writer・
spec-alignment-audit・spec-consistency-check・user-manual-writer・persona-review・
delivery-spec-export）に共通して適用される、絶対禁止事項と運用方針をまとめる。各スキルの `SKILL.md` はこのファイルを参照し、詳細手順内で
個別に矛盾する記述をしない。

> [!NOTE]
> このファイル自体は独立したスキルではない（`name` フロントマターを持たず、ユーザーから
> 直接トリガーされない）。各スキルの `SKILL.md` から相対パス `../共通ルール.md` で読み込まれる。

## 絶対禁止事項

### 1. 機密情報・個人情報の書き込み禁止

**生成・編集するすべてのファイル**（仕様書・実装コード・テストコード・設定ファイル等、種類を
問わない）に、以下を書き込むことを禁止する。インプットのファイルに含まれていても出力には
含めない。

| 種別 | 具体例 |
|------|--------|
| 認証情報 | パスワード、APIキー、アクセストークン、シークレットキー、秘密鍵 |
| 接続情報 | DB接続文字列（ユーザー名・パスワード含むもの）、内部IPアドレス、内部ホスト名 |
| 個人情報 | 氏名、メールアドレス、電話番号、住所、生年月日、マイナンバー等の個人を特定できる情報 |
| その他機密情報 | 本番環境の具体的なURL・エンドポイント、ライセンスキー、証明書の内容 |

- 実装コードで機密値が必要な箇所は `.env.example` 等のプレースホルダーを使い、実際の値を
  コード・コミットに含めない。
- テストコードのフィクスチャ・ダミーデータも実在の個人情報を使わない（`test@example.com` の
  ような明らかなダミー値を使う）。
- 仕様書での記載方法（マスキング等の代替表記）は architecture-design の
  「絶対遵守：記載禁止事項」を参照する。

### 2. 繰り返し処理は最大5回まで

実装↔レビューの修正ループ、テストの再修正ループなど、**同一の問題に対して繰り返し処理を行う
場合は最大5回まで**とする。5回に達してもなお解決しない場合は、ユーザーの意向にかかわらず
その時点で処理を中止し、残っている問題を報告する。**無制限に繰り返し処理を行うことを禁止する。**

- 何を「1回」とカウントするかは、その繰り返しループを定義しているスキルの手順に従う
  （例：spec-implementation の実装後レビューループはレビュー実行回数、spec-dev-cycle の
  テスト再修正ループはテスト実行回数）
- ループ内の自動修正は**3回目のNGまで**（確認不要で修正・再実行してよい）。**4回目のNGは
  ユーザーの承認を得てから**修正し、5回目もNGならユーザーの意向にかかわらず中止する
- 各ループのカウントは独立して行う（例：実装後レビューループとテスト再修正ループは別々に
  最大5回までカウントする）
- ただし多重ループの掛け算で長時間実行になることを防ぐため、**1つの機能に対する1回の
  開発サイクル全体では、コードの修正回数の合計を最大10回まで**とする（全体上限）。
  10回に達したら、各ループの残り回数にかかわらずその時点で処理を中止して報告する
- 上限に達する前でも、ユーザーが中止を選んだ場合はその時点で終了する
- **中止した時点で、それまでに試した修正アプローチ（何をどう直そうとしたか）を報告に残す。**
  ユーザーが同じ問題の修正を再依頼した場合は新しいサイクルとしてカウントし直してよいが、
  前回の報告を踏まえ、失敗した修正アプローチをそのまま繰り返さない

#### カウント対象外：環境起因のエラー

テスト失敗・実行エラーの原因が**コードのバグではなく環境の問題**（依存パッケージ未インストール、
DB・外部サービスの未起動、環境変数・設定の不足、権限不足等）である場合は、修正ループのカウント
対象にしない。コードを修正しても解決しないため、ループを回さず**即座に処理を止めてユーザーに
報告**し、環境側の解消方法を案内する（環境が整ってから再開する）。

### 3. 常駐プロセスの起動禁止

スキルの処理として、**終了しないプロセス（常駐プロセス）を起動することを禁止する。**
処理が永遠に返らなくなり、無制限処理の原因になる。

- テストは必ず**ワンショット実行**する（watch モード禁止）。例：`vitest run`（`vitest` 単体は
  watch になるため不可）、`jest --watchAll=false`、`CI=true npm test` など、1回実行して
  終了する形式を使う
- 開発サーバー・ビルドの watch・デーモン等をスキルの手順として起動しない
  （動作確認にサーバー起動が必要な場合は、起動をユーザーに依頼する）
- テスト・ビルド等のコマンドには適切なタイムアウトを設定し、ハングした場合は打ち切って
  環境起因のエラーとして報告する

### 4. 破壊的コマンドの制限

**プロジェクトフォルダの外に対する削除・移動・破壊的な操作を禁止する。**

- `rm`・`rmdir`・`shred`・`find -delete`・`mv` は、プロジェクトフォルダ内および
  一時ディレクトリ（`/tmp` 等）内のパスに対してのみ使用できる。プロジェクト外のパス
  （上位階層・ホームディレクトリ・システム領域）を対象にしてはならない
- `sudo`・`dd`・`mkfs` 系・`diskutil` の消去系・`shutdown`・`reboot` は場所を問わず使用禁止
- プロジェクト外のファイル操作が必要な場面では、コマンドを実行せずユーザーに手動での
  実行を依頼する

> [!NOTE]
> このルールは指示であると同時に、プラグイン同梱の PreToolUse フック
> （`hooks/check_destructive.py`）によって**強制的にも**ブロックされる。フックに拒否された
> 場合は、同じコマンドを言い換えて再試行せず、ユーザーに状況を報告して指示を仰ぐこと。

### 5. 納品用フォルダ（`docs/納品用/`）の凍結

`docs/納品用/` は `delivery-spec-export` がお客様に提出するために書き出した**成果物**であり、
仕様書ではない。**このフォルダへの読み書きを、以下のとおり禁止する。**

#### 書き込み禁止（一度書き出したら凍結する）

- **仕様書・ソースコードが変更されても、`docs/納品用/` を追従して更新しない。**
  提出済みの資料を後から書き換えると、先方が持っている版と食い違う。内容を変えることは
  「更新」ではなく**納品のやり直し**であり、ユーザーの判断が必要な行為である
- 書き込んでよいのは、**ユーザーが `delivery-spec-export` を明示的に呼び出し、書き出し直しを
  指示したときだけ。** それ以外のどのスキル・どの場面でも、作成・更新・削除・追記をしない
- その書き出し直しは、既定では**前回の書き出し結果に対する差分更新**で行う。変更点を
  「追加 / 更新 / 据え置き / 選択外」に分類して提示し、ユーザーの承認を得てから適用する。
  前回納品したが今回選ばれなかったファイルは、無断で削除も無断で据え置きもせず、
  1件ずつ扱いを確認する
- `docs/納品用/` の**全削除→新規作成は、ユーザーが明示的に作り直しを指示したときだけ**行う。
  差分が多いこと・仕様書が大きく変わったことを理由に、スキル側の判断で全削除に切り替えない
- 仕様書の更新時に「納品用も更新しますか？」と提案することもしない（ユーザーから
  依頼があったときにだけ `delivery-spec-export` を起動する）
- `architecture-design` の再作成モード等で `docs/` を削除する場合も、`docs/納品用/` を
  巻き込みで消さない（個別に確認する）

#### 読み込み禁止（開発・テストの情報源にしない）

- **実装・テスト・レビュー・セキュリティチェック・パフォーマンスチェック・整合性監査の
  いずれにおいても、`docs/納品用/` を読み込まない。** 納品用は社内向け・開発者向けの記述を
  削った版であり、これを正として扱うと誤った実装・テスト・指摘が生まれる
- **仕様の正は常に `docs/` 直下の元の仕様書**（`docs/要件定義書.md`、`docs/画面設計書/` 等）
- `docs/` 配下を走査するときは必ず除外する：

  ```bash
  find docs/ -name "*.md" -not -path "docs/納品用/*" 2>/dev/null | sort
  ```

- 監査系スキル（`spec-alignment-audit`・`spec-consistency-check`）でも対象外。納品用は
  意図的に内容を削っているため、元の仕様書と突き合わせれば必ず「乖離」として検出されるが、
  それは正常な状態であり指摘してはならない

## ドキュメント作成の共通ルール

Markdownのドキュメントを**新規作成・更新するすべてのスキル**（architecture-design・
acceptance-test-writer・user-manual-writer・persona-review・delivery-spec-export 等）に
共通して適用する。

### 同じ種類のGitHub Alertを連続させない

`> [!NOTE]` `> [!IMPORTANT]` `> [!WARNING]` `> [!CAUTION]` `> [!TIP]` のブロックが
**同じ種類で2つ以上連続してはならない。** 1つのブロックにまとめる。

- **なぜ起きるか**：ドキュメントを更新するたびに新しい注記を末尾に足していくと、同種の
  ブロックが並ぶ。書いている側は「今回追加した分」のつもりでも、読む側には**別々の
  注意書き**に見え、どこまでが1つの話なのか分からなくなる
- **まとめ方**：先頭の `> [!TYPE]` の見出しだけを残し、2つ目以降の見出し行を消して、
  本文を `>` だけの行（引用内の空行）で段落として連結する

  ```markdown
  <!-- 悪い例 -->
  > [!NOTE]
  > 1つ目の注記。

  > [!NOTE]
  > 2つ目の注記。

  <!-- 良い例 -->
  > [!NOTE]
  > 1つ目の注記。
  >
  > 2つ目の注記。
  ```

- **種類が違う場合はまとめない**（`NOTE` → `IMPORTANT`、`NOTE` → `WARNING` 等）。
  重要度が違うものを1つにすると、警告が通常の補足に埋もれてしまう
- **既存ファイルを更新するときも同じ。** 注記を追加する場合、直前が同じ種類のブロックなら
  **新しいブロックを作らず、既存のブロックの中に段落として足す**
- 3つ以上連続することもあるため、**1つにまとまるまで繰り返す**

**確認コマンド**（ドキュメントを作成・更新したあとに実行する。`docs/` 以外に出力する
スキルは対象ディレクトリを読み替える）

```bash
python3 - <<'EOS'
import re, pathlib
for p in sorted(pathlib.Path('docs').rglob('*.md')):
    lines = p.read_text(encoding='utf-8').split('\n'); blocks = []; i = 0
    while i < len(lines):
        m = re.match(r'^> \[!(\w+)\]\s*$', lines[i])
        if m:
            st = i; j = i + 1
            while j < len(lines) and lines[j].startswith('>'): j += 1
            blocks.append((st, j, m.group(1))); i = j
        else:
            i += 1
    for a, b in zip(blocks, blocks[1:]):
        if a[2] == b[2] and all(x.strip() == '' for x in lines[a[1]:b[0]]):
            print(f'{p}:{a[0]+1} [{a[2]}] が連続')
EOS
```

## トークン節約方針

### 仕様書は関連するものだけを参照する

`docs/` 配下の仕様書を読み込む際は、**作業対象に直接関連する資料だけを優先して参照する。**
`docs/index.md` や各スキルの「読み込む仕様書」の対応表を使って対象を絞り込み、`docs/` 配下を
無差別に全件読み込むことは避ける。

- 対象が明確な場合（特定の画面・API・機能）は、該当する仕様書ファイルのみを読み込む
- 全体像の把握が必要な場合（要件定義書の参照が必要、複数機能にまたがる等）に**限り**、
  関連する他の資料も参照してよい
- 「システム全体をレビューして」のように対象が広い依頼の場合は、対象範囲を絞ってから
  読み込む（一度に `docs/` 配下の全ファイルを読み込まない）
- **`docs/納品用/` は読み込まない**（絶対禁止事項の「5. 納品用フォルダの凍結」を参照）

### プロジェクト探索時は依存パッケージ・ビルド成果物を除外する

`find` でプロジェクト全体を探索する際は、**依存パッケージ・ビルド成果物・仮想環境の
ディレクトリを必ず除外する。** これらは自前のソースコードではないうえ、`node_modules` だけで
数万ファイルに達することもあり、除外しないと出力がコンテキストを埋め尽くし、実行も遅くなる。

除外は `-not -path` ではなく **`-prune` を使う**（`-not -path` は該当ディレクトリを走査した
うえで出力から除くだけだが、`-prune` はそもそも降りていかないため速い）。

```bash
find . \( -name .git -o -name node_modules -o -name vendor -o -name .venv -o -name venv \
  -o -name __pycache__ -o -name dist -o -name build -o -name .next -o -name target \
  -o -path ./docs \) -prune -o -type f -print | sort
```

- 除外対象：`.git` / `node_modules`（Node）/ `vendor`（PHP・Go）/ `.venv`・`venv`・`__pycache__`
  （Python）/ `dist`・`build`・`.next`（ビルド成果物）/ `target`（Rust・Maven）/ `docs`（仕様書の出力先）
- **`docs` だけは `-name` ではなく `-path ./docs` でプロジェクト直下に限定する。**
  `-name docs` にすると `app/docs/page.tsx`（`/docs` というアプリの画面）や
  `resources/views/docs/` のような**入れ子の docs まで除外され、実装の取りこぼしが起きる**。
  除外したいのは仕様書の出力先である直下の `docs/` だけ。他の除外対象はモノレポ等で
  入れ子になるのが普通なので `-name` のままでよい
- ファイル名で絞り込む場合は、`-prune -o` の**後ろ**に条件を書き、末尾に `-print` を付ける
  （例：`... -prune -o -type f \( -iname "*test*" \) -print`）
- `docs/` 配下の仕様書を探す場合（`find docs/ -name "*.md"`）は探索の起点が異なる別コマンドなので、
  この除外の影響を受けない
