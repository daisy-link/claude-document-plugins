# 仕様書間 整合性チェック・スキル

`docs/` 配下の仕様書どうしを相互参照し、矛盾・参照切れ・抜けを実装着手**前**に洗い出す。
`spec-alignment-audit`（仕様書 vs 実装コード）とは異なり、こちらは**仕様書 vs 仕様書**。
実装が始まる前に直せば、コードまで書いてから発覚するより手戻りが小さい。

> [!IMPORTANT]
> このスキルは**独立して直接呼び出す**。`spec-dev-cycle` の内部スキルではない。
> `architecture-design` は仕様書の作成・更新が一区切りついたタイミングで、このスキルの
> 利用を提案してよい。

> [!CAUTION]
> `../共通ルール.md` に spec-tools プラグイン全体の絶対禁止事項がある。

---

## STEP 1: 前提確認

```bash
find docs/ -name "*.md" -not -path "docs/納品用/*" 2>/dev/null | sort
```

- `docs/` に仕様書が見つからない場合 → 実施せず、次のように案内して停止する：

  > 「`docs/` に仕様書が見つかりません。先に architecture-design スキルで仕様書を作成しますか？」

- 実装コードの有無は問わない（開発前でも実行できる）。

---

## STEP 2: 突き合わせる相互参照

仕様書の種類をまたいだ参照関係を1つずつ確認する。

| 起点 | 参照先 | チェック内容 |
|------|--------|------------|
| 要件定義書の機能一覧 | 画面設計書 / 詳細設計 | 各機能に対応する画面またはAPI・バッチ等が存在するか |
| 画面設計書の「使用API/バックエンド処理」 | 詳細設計（API） | 記載されたエンドポイントが詳細設計に定義されているか |
| 画面設計書のCSV入出力の記載 | 詳細設計（CSV） | リンク先の `CSV_*.md` が実在するか |
| 詳細設計（API等）の「利用画面」欄 | 画面設計書 | リンク先の画面ファイルが実在するか（相互リンク切れ） |
| 詳細設計・画面設計書が言及するテーブル名 | DB設計 | そのテーブル・カラムがDB設計に定義されているか |
| 要件定義書の外部システム一覧 | 詳細設計（外部連携） | 各外部システムに対応する `外部連携_*.md` があるか |

**文言の細かい表現差ではなく、参照先が丸ごと無い・明らかに指しているものが違う、という
レベルの不整合に絞る。** 揺れの範囲内の表現差は対象にしない。

---

## STEP 3: 1件ずつ確認して解決する

見つかった不整合を1件ずつ提示し、その場で対応を選んでもらう。**一覧だけ見せて終わりにしない。**

```
【不整合】要件定義書 F07「在庫アラート通知」に対応する画面・APIが見つかりません。

どうしますか？
(1) 画面設計書または詳細設計に追記する（architecture-design を呼び出します）
(2) 要件定義書から削除する（未実施の機能だった場合）
(3) 保留する（今回は何もしません）
```

```
【不整合】画面設計書 P08_注文詳細画面.md が使う `GET /api/orders/{id}/history` が
詳細設計に見当たりません。

どうしますか？
(1) 詳細設計に追記する（architecture-design を呼び出します）
(2) 画面設計書側の記載を修正する（実際には別のAPIを使っている場合）
(3) 保留する（今回は何もしません）
```

- 修正はすべて `../architecture-design/SKILL.md`（更新モード）を呼び出して行う。
  本スキル自身は `docs/` を直接書き換えない
- **(3) 保留する**を選んだ場合は何もせず次の項目に進み、最終報告に「保留」として記録する

---

## STEP 4: 完了報告

```
【整合性チェック 完了】
- チェックした相互参照: 6種類
- 見つかった不整合: 3件
  - 要件定義書 F07（在庫アラート通知）→ 詳細設計に外部連携（メール送信）を追記
  - 画面設計書 P08 の注文履歴API → 詳細設計に追記
  - 詳細設計 CSV_会員インポート.md への画面設計書リンク切れ → 保留
```

不整合が一切無かった場合は「仕様書間の整合性チェック完了。矛盾・参照切れはありませんでした。」
と報告する。

---

## 品質チェックリスト

- [ ] `docs/` に仕様書が無い場合、実施せず architecture-design を案内している
- [ ] 実装コードの有無を問わず実行している（開発前でも動く）
- [ ] STEP 2の6種類の相互参照をすべて確認している
- [ ] 表現の揺れではなく、参照先が丸ごと無い・明らかに違うというレベルの不整合に絞っている
- [ ] 見つかった不整合を一覧提示だけで終わらせず、1件ずつユーザーに確認して解決している
- [ ] 修正は architecture-design 経由で行っている（本スキル自身が `docs/` を直接書き換えていない）
- [ ] 保留した項目も含め、最終報告に対応結果を明記している
