# 操作マニュアル作成スキル

**システムを実際に日常使う人**（店舗スタッフ・一般利用者等、業務発注者ではない）向けに、
操作方法を教えるマニュアルを作成する。`acceptance-test-writer` は「検収してもらう」ための
チェックリストだが、本スキルは「使い方を覚えてもらう」ための手順書という違いがある。

> [!IMPORTANT]
> このスキルは**独立して直接呼び出す**。`spec-dev-cycle` の内部スキルではない。

> [!CAUTION]
> `../共通ルール.md` に spec-tools プラグイン全体の絶対禁止事項がある。実在の個人情報・
> 機密情報を書き込まない。

---

## STEP 1: 前提確認

```bash
find docs/画面設計書 -name "*.md" 2>/dev/null | sort
```

- `docs/画面設計書/` が無い場合 → 作成せず、次のように案内して停止する：

  > 「`docs/画面設計書/` が見つかりません。操作マニュアルの作成には画面設計書が必要です。
  > 先に architecture-design スキルで仕様書を作成しますか？」

## STEP 2: 新規作成 or 更新の判定

| 判定条件 | モード |
|---------|--------|
| `docs/操作マニュアル.md` が存在しない | **新規作成モード** → STEP 3へ |
| 存在する（画面・機能が追加された等で更新したい） | **更新モード** → STEP 5へ |

## STEP 3: 章立ての決定

`docs/画面設計書/index.md` の画面一覧・画面フローを読み込み、利用者にとって自然な順番・
グルーピングで章立てを決める。

- 基本は画面フロー（遷移の流れ）に沿った順序にする（例：ログイン → 一覧 → 詳細 → 登録）
- 認証要否（管理者専用の画面等）から見て、**明らかに利用者の役割が分かれている**場合は
  「一般利用者向け」「管理者向け」のように章を分ける。役割が1種類しかないシステムでは
  分けなくてよい
- 技術的なカテゴリ分け（画面設計書のP01・P02...の並び）をそのまま使う必要はない。
  利用者が「何をしたいか」を軸に並べ替えてよい

## STEP 4: 各章の作成（新規作成）

画面ごとに、以下を平易な言葉・手順書きで作成する。

```markdown
## 〇〇をする

### この機能でできること

（要件定義書があれば、その機能が何のためにあるかを一言添える）

### 手順

1. 〇〇画面を開きます（メニューの「〇〇」から移動できます）
2. 〇〇を入力します
3. 「登録」ボタンを押します

### 画面イメージ

（スクリーンショットがあれば掲載。無ければ省略）

### よくあるつまずきポイント

（入力バリデーションの内容から、間違えやすい点を先回りして書く。例：
「メールアドレスは半角で入力してください」）
```

### スクリーンショットの扱い

- `docs/画面設計書/images/` に既にスクリーンショットがあれば、そのまま流用する
- 無い場合は、**このマニュアル作成時に取得してよいかユーザーに確認する**：

  > 「この画面のスクリーンショットはまだ無いようです。開発サーバーを起動して撮影してもよいですか？」

  OKが出たらPreview系ツールで撮影し `docs/画面設計書/images/` に保存する（画面設計書側の
  スクリーンショット取得手順に準じる）。断られた場合や取得できない画面は、文章だけで説明する

### 用語

技術用語（API・ステータスコード・DB等）は使わない。画面設計書の「入力バリデーション」に
書かれた制約は、エラーメッセージではなく**利用者への案内**として書き直す
（例：「バリデーションエラー」ではなく「〇〇は必須項目です」）。

## STEP 5: 保存・更新

出力先は `docs/操作マニュアル.md`（システム名を含めない、資料名のみ）。

**新規作成の場合**：STEP 3・4の内容でファイルを作成する。`docs/index.md` が存在すれば、
ドキュメント一覧に1行追加する（無ければ追加しなくてよい）。

**更新モードの場合**：

1. `docs/画面設計書/` を読み込み、前回作成時から**新しく増えた画面・変更された画面**を検出する
2. 新しく増えた画面は、章立ての適切な位置に新しい章を追加する
3. 内容が変わった画面は、該当する章だけを更新する（関係の無い章は書き換えない）
4. 削除された画面の章は削除してよい（検収文書と異なり、これは「今使えること」を説明する
   文書のため、現状に無い操作の説明を残す必要はない）
5. 更新した旨を報告する

## STEP 6: Word/PDF出力（希望があった場合のみ）

**`docs/操作マニュアル.md` が正であり、Word/PDFはそこから作る追加のオプション出力。**
ユーザーから明示的に要望されたときだけ行う。

- 「Wordでもほしい」→ `docx` スキルで `docs/操作マニュアル.docx` を生成する
- 「PDFでもほしい」→ `pdf` スキルで `docs/操作マニュアル.pdf` を生成する
  （Word版を作った流れであれば、それを変換する形でもよい）
- どちらも見出し構成・画像は Markdown と揃える

## 品質チェックリスト

- [ ] `docs/画面設計書/` が無い場合、作成せず architecture-design を案内している
- [ ] 技術用語を避け、利用者が読んで迷わない平易な言葉で書かれている
- [ ] 手順が「まず〇〇する、次に〇〇する」のように具体的な操作順で書かれている
- [ ] 章立てが技術的な画面番号順ではなく、利用者にとって自然な順序・グルーピングになっている
- [ ] スクリーンショットは既存のものを流用し、無い場合は取得可否をユーザーに確認している
- [ ] 入力バリデーションの内容が、エラーメッセージの丸写しではなく利用者への案内として書かれている
- [ ] 実在の個人情報・機密情報を書き込んでいない
- [ ] **（更新モード）** 変更の無い章をそのまま保持し、変更・追加された章だけ更新している
- [ ] **（Word/PDF希望時）** 自動では生成せず、要望があったときだけ生成している
- [ ] 出力先が `docs/操作マニュアル.md`（システム名を含まない）になっている
- [ ] 同じ種類のGitHub Alert（`> [!NOTE]` 等）が連続していない（`../共通ルール.md` の「ドキュメント作成の共通ルール」。連続する場合は1つのブロックにまとめる）
