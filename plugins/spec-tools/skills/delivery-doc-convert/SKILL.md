# 納品用資料のHTML版・PDF版を作る

`docs/納品用/Markdown/` の納品用仕様書を、お客様に配布できる2つの形に変換する。

| 形 | 出力先 | 向いている場面 |
|---|---|---|
| HTML（静的サイト） | `docs/納品用/HTML/` | 画面で読む・共有フォルダに置く・リンクをたどって探す |
| PDF（1冊に統合） | `docs/納品用/PDF/` | 納品・印刷・メール添付・製本 |

どちらも同じ変換処理を通すので内容は必ず一致する。

> [!IMPORTANT]
> **このスキルは内容に手を入れない。** Markdown版に書かれていることを、決まった体裁の
> HTML・PDFに**変換するだけ**。文面の修正・要約・追記が必要なら `delivery-spec-export` の
> 仕事であり、**元の `docs/納品用/Markdown/` を直してから変換し直す**。

> [!IMPORTANT]
> **同梱スクリプトが変換を全部やる。HTML・CSSを手書きしない。** 案件が変わっても同じ体裁に
> なることに価値があるため、独自レイアウトを作らない。

> [!CAUTION]
> `../共通ルール.md` に spec-tools プラグイン全体の絶対禁止事項がある。**社外に出る文書**で
> あるため、`docs/納品用/` の凍結ルール（「5. 納品用フォルダの凍結」）に従う。

---

## 絶対ルール

1. **変換元は `docs/納品用/Markdown/` のみ。** `docs/` 直下の社内用仕様書（`docs/要件定義書.md`・
   `docs/画面設計書/` 等）は変換しない。社内用には `[要確認]`・TODO・内部ホスト名・社内担当者名が
   残っており、**表紙と目次の付いた配布物にすると、そのまま提出される事故が起きる**。
   ユーザーが「`docs/` をHTMLにして」と言った場合も、このスキルでは実行せず理由を伝えて確認する
2. **書き込むのは `docs/納品用/HTML/` と `docs/納品用/PDF/` だけ。** `docs/納品用/Markdown/` と
   `docs/` 直下は読み取り専用として扱う
3. **内容を書き換えない。** 変換の過程で文面を直さない。誤字・記述の問題に気づいた場合は、
   自分で直さずユーザーに報告する（直すのは `delivery-spec-export` の役割）
4. **ユーザーが指示したときだけ変換する。** 仕様書やMarkdown版が更新されたことを理由に、
   自動で変換し直さない。他のスキルの作業中に「HTML版も更新しますか？」と提案することもしない
   （`../共通ルール.md` の「5. 納品用フォルダの凍結」）
5. **中身が一致しない状態で納品しない。** 図が描画できていない・点検で警告が残っている場合は、
   「できました」と報告しない（STEP 4・STEP 6）

## 他スキルとの関係

```
docs/納品用/
├── Markdown/   ← delivery-spec-export が書き出す（原本）
├── HTML/       ← 本スキルが変換して生成
└── PDF/        ← 本スキルが変換して生成
```

`Markdown/` を書き出し直したら、**HTML・PDFは変換し直さないと内容が食い違う。**
`delivery-spec-export` は変換を行わないため、ユーザーがこのスキルを呼んだときに反映される。

## STEP 1: 前提確認

```bash
# 変換元（納品用Markdown版）があるか
find docs/納品用/Markdown -name "*.md" 2>/dev/null | sort

# 前回の変換結果があるか
ls docs/納品用/HTML docs/納品用/PDF 2>/dev/null
```

- `docs/納品用/Markdown/` が無い・空の場合 → 変換せず、次のように案内して停止する：

  > 「`docs/納品用/Markdown/` に納品用の仕様書が見つかりません。変換には納品用のMarkdown版が
  > 必要です。先に delivery-spec-export スキルで書き出しますか？」

- `docs/納品用/Markdown/index.md` が無い場合 → 資料の並び順とトップページを決められない。
  `delivery-spec-export` での書き出しをやり直すよう案内する

### 必要なもの

| 用途 | 必要なもの | 不足時 |
|---|---|---|
| HTML | Python 3・`markdown` | `pip3 install markdown` |
| PDF | 上記＋`pypdf`・Google Chrome | `pip3 install pypdf` / Chrome はユーザーに導入を依頼 |
| 図（mermaid） | インターネット接続 | **オフラインでは図がテキスト表示になる。その状態で納品しない** |

## STEP 2: 作る形式を決める

ユーザーの指示で形式がはっきりしている場合（「PDFにして」等）はそれに従う。
**はっきりしない場合は `AskUserQuestion` で選ばせる**（HTML版 / PDF版 / 両方）。

- **迷ったらHTML版を先に作る。** 目視確認が早く、直すべき点が先に分かる
- PDFだけを頼まれた場合も、HTML版を先に作ってから進めてよい
- **PDFは100ページ規模で1分前後かかる。** 実行前にその旨を伝えておく

### 表紙・ヘッダーに出す名前を確認する

`--title`（会社名・システム名）と `--subtitle`（`仕様書` 等）は**お客様の目に最初に入る文字**。
省略すると `docs/納品用/Markdown/index.md` の見出しがそのまま使われる。

- `index.md` の見出しをそのまま出してよいかを確認する。社名の表記（正式名称か略称か）は
  お客様との取り決めがあるため、**推測で補わずユーザーに確認する**

## STEP 3: HTML版に変換する

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/delivery-doc-convert/scripts/build_html.py" \
  --src docs/納品用/Markdown --out docs/納品用/HTML \
  --title "○○株式会社" --subtitle "△△システム 仕様書"
```

| 引数 | 内容 |
|---|---|
| `--src` / `--out` | **常に上記の納品用パスを指定する**（既定値は `docs` / `HTML` なので省略しない） |
| `--title` | ヘッダー左に出る名前。省略時は `index.md` の見出し |
| `--subtitle` | ヘッダーの補足（例: `仕様書`）。省略可 |
| `--home-label` | トップページの呼び名（既定: `ドキュメント一覧`） |
| `--style` | 差し替え用CSS（「見た目を変えたいと言われたら」を参照） |

- **`docs/納品用/HTML/` は毎回まるごと作り直される。** 手で足したファイルは消えるため、
  HTML側には何も置かない。置いてあるものがないか STEP 1 で確認しておく
- 資料の並び順は `docs/納品用/Markdown/index.md` のリンク順をそのまま使う。
  並びがおかしいときは**スクリプトではなく `index.md` を直す**が、`index.md` は
  `delivery-spec-export` の成果物なので、**勝手に直さずユーザーに報告する**

## STEP 4: 点検する（必須）

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/delivery-doc-convert/scripts/check_output.py" docs/納品用/HTML
```

ページ数・リンク切れ・変換漏れ（図や注記の差し込み残り、`.md` のままのリンク）を出す。
**0件でないまま「できました」と報告しない。**

| 症状 | 対処 |
|---|---|
| リンク切れ | 元のMarkdown版のリンクが納品用の中で完結していない。**自分で直さず**、`delivery-spec-export` 側の問題としてユーザーに報告する |
| `.md` のままのリンク | 同上（変換対象外のファイルを指している可能性） |
| 図・注記の差し込み残り | 記法の誤り。該当箇所をユーザーに報告する |

見た目まで確かめたいときは、ローカルサーバで開く（`file://` だと相対パスの都合で
スタイルが当たらない環境がある）。

```bash
python3 -m http.server 8765 -d docs/納品用/HTML
```

> [!CAUTION]
> 確認が終わったら**必ずサーバを止める**（`../共通ルール.md` の常駐プロセスの起動禁止）。

## STEP 5: PDF版に変換する

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/delivery-doc-convert/scripts/build_pdf.py" \
  --src docs/納品用/Markdown --out docs/納品用/PDF \
  --title "○○株式会社" --subtitle "△△システム 仕様書"
```

- 出力は `docs/納品用/PDF/<タイトル>_<サブタイトル>.pdf` の1ファイル（`--name` で指定可）
- 表紙（主題・副題・日付。`--date` で指定、既定は本日）→ 目次（章番号とページ番号）→ 全資料の順
- 全ページの下に「資料名 と ページ/総ページ」。表紙には入れない
- 資料間のリンクはPDF内のジャンプになる
- A4縦・余白18mm前後

> [!IMPORTANT]
> **`docs/納品用/PDF/` は作り直さない（過去のPDFが残る）。** 同名なら上書きされるが、
> `--title` や `--date` が変わるとファイル名も変わり、**古いPDFが並んで残る**。
> 提出時に旧版を渡す事故になるため、残っている旧版をSTEP 6で必ず報告し、
> **削除するかどうかはユーザーに確認する**（自分で削除しない）。

**目次のページ番号を正確にするため、内部で2回印刷している**（1回目で各資料の開始ページを調べ、
2回目で目次に反映する）。

### 仕上がりの確認

ページ数・目次のページ番号・**図が絵になっているか**を見る。macOSならページを画像化できる。

```bash
python3 -c "from pypdf import PdfReader,PdfWriter; r=PdfReader('docs/納品用/PDF/仕様書.pdf'); w=PdfWriter(); w.add_page(r.pages[1]); w.write(open('/tmp/p2.pdf','wb'))" && sips -s format png -Z 1100 /tmp/p2.pdf --out /tmp/p2.png
```

## STEP 6: 報告

出力先のパス・ページ数・点検結果を伝える。あわせて次も伝える。

```
【納品用資料の変換完了】
- HTML版: docs/納品用/HTML/（15ページ・点検 0件）
- PDF版:  docs/納品用/PDF/○○株式会社_△△システム_仕様書.pdf（全82ページ）
- 変換元: docs/納品用/Markdown/（内容は変更していません）

■ お伝えすること
- Markdown版を書き出し直したら、同じ手順で変換し直してください（自動では追従しません）
- 図（画面遷移図・ER図）は描画ライブラリをCDNから読むため、完全オフラインの環境では
  図がテキスト表示になります

⚠️ docs/納品用/PDF/ に旧版が1件残っています（○○株式会社_△△システム_仕様書_20260401.pdf）。
提出時に取り違えないよう、削除するかどうかご指示ください。
```

- HTML版だけを作った場合は、**PDF版も同じ内容で作れること**を添えて必要かどうか聞く
- 点検で警告が残っている場合は、**件数と内容をそのまま報告する**（消さない・伏せない）

## 図の扱い（ここは触ると壊れやすい）

図は**印刷の前に別のブラウザ実行で1枚ずつ描き起こし、SVGとして本文に貼り込んでから**印刷している。
印刷と同時に描かせると、描画の途中で紙面が確定してしまい、図が空になったり2つの図が重なったりする。
さらに、図はライブラリに任せず**こちらでIDを振って1枚ずつ順番に描かせている**。まとめて描かせると
IDが同じミリ秒で衝突し、1枚のSVGに複数の図が混ざる・別の図が空になる、という壊れ方をする。

図が空・図どうしが重なる・4.1の図が消えて4.2に混ざる、といった症状が出たら、この描き起こしの部分
（`build_pdf.py` の `prerender_mermaid`）を疑う。事前描画に失敗した場合はメッセージを出して
従来どおり印刷時描画に落ちるので、そのメッセージが出ていないかも確認する。

1ページに収まらない大きな図は、`assets/print.css` の `.mermaid-wrap svg { max-height: 225mm }` で
縮めている。図が小さすぎると言われたらこの値を調整する（大きくすると図がページをまたいで分断される）。

## Markdownの記法がどう変換されるか

| Markdown | HTML版での見え方 |
|---|---|
| `> [!NOTE]` `[!IMPORTANT]` など | 「補足」「重要」などのラベル付きの囲み |
| ` ```mermaid ` | 図として描画（画面遷移図・ER図） |
| 表 | 横に長い場合はその表だけ横スクロール |
| `[← 一覧に戻る](./index.md)` | パンくずと重複するため自動で削除 |
| 資料間の `.md` リンク | `.html` に自動で置換（表示文字列も含む） |

各ページの構成は固定。

- 左サイドバーに全資料の一覧（現在ページをハイライト、フォルダは見出し兼リンク）
- 本文の上にパンくず、下に前後の資料へのリンク
- 本文は2カラム（サイドバー＋本文）で、本文エリアを最大限広く取る
- 画面幅820px以下ではサイドバーを ☰ に格納（JavaScript不要）
- 印刷時はナビ類を落として本文だけ出す

## 表の折り返しルール

表は読み合わせに使われるため、「No」「項目名」のような短い列が2行に割れると読みにくい。
かといって全部を折り返し禁止にすると横に伸びて読めなくなるので、2段構えで判定している。

1. **列全体が短い場合** … 列の最大幅が `NOWRAP_WIDTH`（既定24＝全角12文字）以下なら折り返さない
2. **名称を並べる列** … 見出しが `LABEL_HEADERS`（`項目` `項目名` `機能` `状態` など）に入っている列は、
   1マスずつ見て `LABEL_NOWRAP_WIDTH`（既定40＝全角20文字）以下なら折り返さない

いずれも `scripts/build_html.py` の先頭で調整できる。「この列も1行にしたい」と言われたら、
まず `LABEL_HEADERS` にその見出し名を足すのが最短。数値を上げすぎると表が画面からはみ出して
横スクロールが増えるので、変更したら幅1280px程度でも確認する。

## 見た目を変えたいと言われたら

色・余白・文字サイズは、HTML版が `assets/style.css`、PDF版が `assets/print.css` の
先頭にある `:root` の変数にまとまっている（`--accent` がアクセント色、`--sidebar-w` がサイドバー幅、
PDFの用紙と余白は `@page`）。案件ごとに色だけ変えたい場合は、どちらのスクリプトも `--style` で
差し替え用のCSSを渡せる。

> [!IMPORTANT]
> **片方だけ直すと2つの版で見た目がずれる。色を変えるときは必ず両方直す。**
> また、プラグイン同梱のCSSを直接書き換えると他の案件にも影響するため、案件ごとの調整は
> **プロジェクト内にコピーしたCSSを `--style` で渡す**。

レイアウトそのものを大きく変える依頼（資料ごとに別PDFにしたい、A3にしたい等）は、このスキルの
範囲外。その場合は別フォーマットとして新しく作り、このスキルの出力は今のまま残す
（過去案件と同じ体裁で再生成できることがこのスキルの価値のため）。
